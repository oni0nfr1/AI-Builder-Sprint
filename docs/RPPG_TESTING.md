# rPPG 비교 테스트

개발 전용 화면에서 `rppg-web`과 기존 서버 CHROM을 단독으로 교대 측정한 뒤,
마지막에 같은 15초 영상 구간에서 동시에 분석한다. 원본 영상은 전송하지 않는다.
레거시 분석에 필요한 얼굴 ROI의 RGB 평균 시계열만 localhost 백엔드로 보내고
DB에는 저장하지 않는다.

## 실행

백엔드 `.env`에서 진단 API를 명시적으로 연다.

```env
RPPG_DIAGNOSTICS_ENABLED=true
```

평소처럼 프론트엔드와 백엔드를 실행한 뒤 아래 주소를 연다.

```text
http://localhost:5173/rppg-test
```

이 화면은 Vite 개발 모드에서만 노출된다. 백엔드 스위치의 기본값도 `false`라서
프로덕션에서 RGB 시계열 수집 경로가 우연히 열리지 않는다.

## 측정 순서

화면이 아래 7단계를 차례로 안내한다.

1. 1세트: rppg-web → CHROM
2. 2세트: CHROM → rppg-web
3. 3세트: rppg-web → CHROM
4. 마지막: 두 알고리즘 동시 측정

세트별 선후 순서를 바꿔 시간 경과와 안정화 효과가 한 알고리즘에만 유리하게
작용하지 않도록 한다. CHROM 단독 단계에서는 rppg-web 세션을 완전히 종료해
CPU/GPU 경쟁을 없앤다. web 단계는 새 tracker가 안정 상태가 되거나 12초의 고정
워밍업이 끝난 뒤 측정 버튼이 열린다. 품질이 낮아도 측정할 수 있게 두는 이유는
실패 사례를 제외해 성공률을 부풀리지 않기 위해서다.

각 단계 직전에 가슴 스트랩이나 산소포화도계의 **현재 기준 BPM을 갱신**한다.
점이 보이는 동안 15초간 정지하고, 측정 사이에는 가능하면 20~30초 쉬어 심박을
안정시킨다. 7단계가 끝나면 JSON 또는 CSV를 내려받는다.

권장 조건은 밝은 정면광, 보통 실내광, 어두운 조명, 작은 고개 움직임,
발화 직후 정지, 가벼운 운동 직후다.

## 주요 지표

- 기준 장비 대비 두 알고리즘의 절대 오차와 MAE
- `confidence >= 0.4` 통과율
- 단독 측정의 기준 장비 대비 오차와 마지막 동시 측정의 두 알고리즘 BPM 차이
- 실측 FPS, 샘플 수, 평균 밝기, ROI 수
- rppg-web signal quality, estimator agreement, reason code

기준 BPM을 입력하지 않으면 알고리즘 간 일치도는 볼 수 있지만 실제 정확도는
판단할 수 없다.

## 구현 경계

- 프론트엔드 화면은 Vite 개발 모드의 `/rppg-test`에서만 열린다.
- 백엔드 `/diagnostics/rppg/compare`는 `RPPG_DIAGNOSTICS_ENABLED=true`일 때만 열린다.
- 진단 API는 RGB 평균 시계열로 CHROM을 즉시 계산할 뿐 storage 계층을 호출하지 않는다.
- 프로덕션 세션의 `/captures` 계약과 저장 데이터에는 영향을 주지 않는다.
- 알고리즘 하나만 실행한 결과와 두 알고리즘을 함께 실행한 결과를 모두 받을 수 있다.

## 2026-08-03 실측 결과

원자료는 저장소 루트의 `rppg-comparison.csv`와
`rppg-comparison-alternating.csv`에 보존한다. 두 파일 모두 참가자는 익명 ID `P01`,
조건은 `normal_light_still`이다.

### 1차 — 동시 측정 7회, 기준값 없음

| 지표 | rppg-web | 서버 CHROM |
|---|---:|---:|
| 결과 생성 | 6/7 | 7/7 |
| `confidence >= 0.4` | 5/7 | 0/7 |
| 평균 confidence | 0.691 | 0.180 |
| BPM 범위 | 93.6~98.0 | 76.5~218.5 |

rppg-web의 생성값은 표준편차 1.55 BPM으로 반복성은 높았지만 기준 심박이 없어
정확도는 판단할 수 없었다. CHROM은 모든 측정에서 confidence 기준을 통과하지 못했다.
마지막 두 측정의 레거시 샘플링이 6.53fps와 5.02fps로 떨어져, 동시 실행이 비교
자체를 오염시킬 가능성이 드러났다. 이 결과를 계기로 단독 교대 프로토콜을 만들었다.

### 2차 — 단독 교대 3세트 + 마지막 동시 측정

| 구분 | 결과 생성 | `confidence >= 0.4` | 기준 BPM 대비 절대 오차 |
|---|---:|---:|---|
| rppg-web 단독 | 2/3 | 2/3 | 7.89, 0.05 BPM |
| CHROM 단독 | 3/3 | 0/3 | 69.2, 20.0, 7.9 BPM |
| rppg-web 동시 | 1/1 | 1/1 | 0.94 BPM |
| CHROM 동시 | 1/1 | 0/1 | 84.5 BPM |

rppg-web은 생성에 성공한 세 번 모두 confidence 기준을 통과했고 MAE는 2.96 BPM이었다.
다만 적용 4회 중 첫 단독 측정은 결과를 만들지 못해 coverage는 75%다.

CHROM은 단독·동시 네 번 모두 confidence 기준을 통과하지 못했다. 단독 측정의
원시 MAE는 32.37 BPM, 동시 측정 오차는 84.5 BPM이었다. 모든 SNR이 음수였으므로
이 값은 제품 판정에서 제외되는 것이 맞다.

동시 측정의 레거시 FPS는 20.25로, 후반 단독 CHROM의 20.33~20.35fps와 비슷했다.
따라서 1차 실험의 5~6fps 급락을 동시 실행 하나로 설명할 수는 없다. 반면 조명,
ROI 수, 중복 샘플 문제가 없는 조건에서도 CHROM 오차가 컸으므로 현재 구현의
신호 추정 안정성 문제는 남아 있다.

## 현재 판단

- MVP 주 경로는 rppg-web을 유지한다.
- `CONFIDENCE_FLOOR=0.4`는 낮추지 않는다.
- 서버 CHROM은 기존 데이터와 실패 환경을 위한 호환 폴백으로만 유지한다.
- CHROM confidence가 기준 미달이면 지금처럼 심박을 제외하고 음성 신호로 진행한다.
- 이 결과만으로 rppg-web의 일반 정확도를 주장하지 않는다. 참가자 1명, 조건 1개의
  탐색 실험이기 때문이다.

rppg-web에도 미해결 신호가 있다. 성공 측정 모두 `LOW_SNR`이었고 estimator
agreement는 0.17~0.23으로 낮았다. 한 측정은 `stable_sample_count=1`인데 confidence가
0.886이었으며, 첫 측정은 12초 워밍업 뒤에도 결과가 없었다. agreement나 안정 샘플
임계값을 지금 추가하면 정확했던 값까지 모두 제외될 수 있으므로 표본을 더 모으기
전에는 게이트를 바꾸지 않는다.
