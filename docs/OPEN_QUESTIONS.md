## Q1. 순서 효과(Order Effect) 보정

**문제**
선택지 A를 먼저, B를 나중에 말하면 심박이 시간에 따라 자연 안정화되어 **뒤에 말한 쪽이 항상 차분해 보이는 편향**이 생긴다. 음성도 뒤로 갈수록 긴장이 풀린다.

**MVP 대응 (임시)**
선택지 제시 순서를 랜덤화하고, 리포트에 순서를 표기한다.

**나중에 검토할 것**
- `A→B→A` 3회 측정으로 재현성 확인 (A의 두 측정이 일관되면 신호가 진짜)
- 세션 간 순서 교대 (다음 세션에서는 B부터)
- 시간 경과에 따른 drift를 회귀로 추정해 보정
- 선택지가 3개 이상일 때 조합 폭발 문제

**보류 이유** — 골자를 먼저 세우고, 실제 데이터에서 편향 크기를 측정한 뒤 결정하는 게 맞다.

## Q2. Essentia.js 부분 도입

**조사 결과 (2026-08-02)**
Essentia에는 **jitter / shimmer / HNR이 없다.** MIR(음악 정보 검색) 중심 라이브러리라 voice quality 지표를 다루지 않는다.
- 있음: `PitchYin`, `PitchYinFFT`, `Energy`, `ZeroCrossingRate`, `SpectralCentroid`, MFCC 계열
- 없음: jitter, shimmer, HNR ← eGeMAPS voice quality 축의 핵심

**결정** — openSMILE(백엔드) 유지. Essentia.js로 대체하지 않는다.

**나중에 검토할 것**
브라우저에서 돌아간다는 장점이 있으므로 **보조 용도**로는 매력적:
- 녹음 중 실시간 피드백 ("신호 잘 잡히고 있어요")
- 오디오 원본을 서버에 안 보내는 경로 → 프라이버시 전제와 정합
- 다만 이중 구현 복잡도가 늘어나므로 골자가 선 뒤에 판단

## Q3. rPPG 정확도 개선

**현황**
웹캠 rPPG로 BPM은 조명이 괜찮으면 나오지만, **HRV는 30fps 웹캠으로 신뢰하기 어렵다.**
상대 변화율 방식이라 약점이 상당 부분 상쇄되지만, 정확도를 조금이라도 올리고 싶다.

**첫 실측 (2026-08-02) — 심박이 통째로 버려졌다**
```
bpm 156.1   confidence 0.052   snr_db -8.96   → excluded_metrics: ["bpm"]
ROI 평균 밝기 45/255   15초에 731샘플(48.7fps)
```
원인 두 가지를 찾아 고쳤다.

1. **프레임 중복** — `requestAnimationFrame`은 디스플레이 주사율(60~120Hz)로 도는데
   카메라는 30fps라, 약 38%가 직전 프레임의 복사본이었다. 같은 값이 반복되면 계단
   신호가 생기고 그 가짜 고주파를 FFT가 심박으로 잡는다.
   → `requestVideoFrameCallback`으로 실제 프레임에만 샘플링. 미지원 브라우저는
   `currentTime` 변화로 중복을 거른다.
2. **조명 부족** — 밝기 45면 맥동이 양자화 노이즈에 묻힌다.
   → 캡처 **전** 준비 화면에서 신호를 미리 보여준다. 측정 중에만 경고하면 이미
   15초가 흐른 뒤라 늦다.

**2차 실측 (2026-08-02, 위 두 수정 후) — 방향은 맞았으나 아직 미달**
```
샘플링   731샘플 48.7fps  →  438샘플 29.1fps   ✅ 중복 0, 카메라 fps와 일치
밝기     45.0             →  65.9 / 67.8 / 70.8 ✅ 기준(60) 초과

bpm         156.1  →  112.2 / 60.2 / 76.1     (생리적으로 가능한 범위로 진입)
confidence  0.052  →  0.193 / 0.253 / 0.299   (3.7~5.7배 개선, 그러나 0.4 미달)
snr_db      -8.96  →  -6.13 / -4.94 / -4.02   (여전히 음수 = 노이즈가 신호보다 크다)
```
→ `excluded_metrics: ["bpm"]`. **두 세션 연속으로 심박이 상태축·선호축에서 빠졌다.**

원인 진단은 맞았지만 쉬운 개선은 여기서 소진됐다. 남은 카드는 **다중 ROI 융합**과
**모션 보정**이고, 둘 다 아래 "시도해볼 것"에 이미 적혀 있던 항목이다.

**교체 후보: `@elata-biosciences/rppg-web`** (MIT, v0.14.0, Rust→WASM)
- 있는 것: CHROM(우리와 동일 계열) + `multiRoiFusion`(이마+볼) + `CaptureConfidenceScorer`
  (모션·조명 게이팅) + 베이지안 BPM 트래커 + 진단 코드(`low_skin_ratio` 등)
- ⚠️ **구조적 충돌**: "~10초 워밍업 후 첫 BPM". 우리 상상 구간은 15초이고 창 세 개를
  각각 재서 비교하는 설계라, 연속 트래커의 시간축 스무딩이 그 경계를 뭉갠다.
  중립 imagine 15초를 워밍업으로 쓰면 풀릴 수 있으나, 사이에 낀 발화 10초에서
  얼굴이 움직여 트래커가 오염된다. `stop()`/`start()`로 끊으면 다시 워밍업.
- ⚠️ `[2]`가 서버→브라우저로 넘어가므로 계약이 바뀌고(`rgb_series` → 클라이언트 `hr`),
  **저장된 세션 재분석이 불가능해진다.**
- ⚠️ pre-1.0, 정확도 벤치마크 미공개, Vite 7 기준 WASM 설정 필요(우리는 Vite 6)

**미결** — 교체할 것인가, `CONFIDENCE_FLOOR`(0.4)를 낮출 것인가, 우리 구현에 다중 ROI를
직접 넣을 것인가. 상대 변화율 방식이라 절대 정확도가 덜 중요하다는 논거가 있지만,
SNR이 음수라는 건 그 상대 변화조차 신뢰하기 어렵다는 뜻이다.

**시도해볼 것**
- ROI 선택: 이마 / 볼 / 다중 ROI 가중 평균 중 무엇이 안정적인가
- 색공간: RGB green 채널 단독 vs CHROM vs POS 알고리즘
- 움직임 보정: 얼굴 랜드마크 기반 motion artifact 제거
- 프레임레이트: 60fps 요청이 가능한 환경에서 HRV까지 노려볼 수 있는가
- 측정 구간: "상상 15초" 정지 구간이 실제로 발화 중보다 얼마나 나은지 정량 확인
- 조명 가이드 UX (얼굴에 광원, 역광 경고)

**계약** — `hr` 필드에 `confidence`를 항상 함께 반환한다. 신뢰도가 낮으면 리포트에서 심박 축을 빼고 음성만으로 간다.

## Q4. 디폴트(평소) 상태의 정의

**두 축의 역할 분리 (혼동 주의)**
```
Δ(A, B)            →  선호   "어느 쪽에 마음이 가 있는가"
(A,B) vs default   →  상태   "지금 이 사람은 어떤 상태에서 이 기록을 남겼는가"
```
**default는 선호 신호가 아니다.** 선호는 오직 A와 B의 차이에서 나온다.
default는 그 차이를 어떤 조건에서 읽어야 하는지 알려주는 **프레임**이다.
같은 Δ(A,B)라도 `calm` 상태에서 나온 것과 `aroused` 상태에서 나온 것은 신뢰도가 다르다.

**원래 의도**
스마트워치 등으로 생체 데이터를 **지속 수집**해서 "이 사람의 평균적인 상태"를 확보하는 것.
"지금 이 사람이 어떤 상태인가"를 알려면 그 사람의 평소를 알아야 하고,
그건 세션 안에서 20초 재는 것보다 지속 수집이 압도적으로 정확하다.

**MVP 대응 (임시)**
세션 시작마다 20초 **중립 앵커** 구간 (고민과 무관한 발화 — "오늘 아침에 뭐 하셨어요?").
rPPG 워밍업을 겸하므로 사용자에겐 "측정 준비 중"으로 보인다.
세션이 쌓이면 중립 앵커들의 평균이 개인 디폴트로 수렴.

**계약**
```
baseline_source: "session_neutral" | "accumulated" | "continuous_wearable"
```
`[3] 상대화` 단계만 갈아끼우면 웨어러블 지속 수집으로 이행 가능하게 유지한다.

**나중에 검토할 것**
- 중립 앵커가 실제로 중립인가? (아침 얘기가 누군가에겐 스트레스일 수 있음)
- 시간대/컨디션에 따른 디폴트 변동을 어떻게 다룰 것인가
- 웨어러블 연동 시 어떤 API (Web Bluetooth? Health Connect? Apple HealthKit?)

## Q6. 판정 임계값·부호 테이블 튜닝

**현황**
`app/services/analysis_service.py`의 값들은 직관_노트.pdf의 패턴 서술("음성 톤 하강 + 생체 저하 → 내적 충돌", "피치 상승 + 말속도 증가 → 몰입")에 근거한 **규칙 기반 휴리스틱**이다. 실측 데이터로 검증한 값이 아니다.

```
PREFERENCE_THRESHOLD    = 0.08
AROUSAL_THRESHOLD       = 0.10
CONTRADICTION_THRESHOLD = 0.08
EXTREME_DELTA           = 0.80   (이 크기 이상이 2개면 조건 차이로 보고 신뢰도 ×0.6)
ENGAGEMENT_SIGN / HR_ENGAGEMENT_SIGN / AROUSAL_SIGN  (부호·가중치 테이블)
```

**실측에서 추가된 것 — 측정 조건 차이 (2026-08-02)**
첫 세션에서 `loudness_mean -0.803`, `f0_std -1.102`가 동시에 나왔다.
`_symmetric_ratio`의 최대 크기가 ±2이므로 이건 거의 극단값인데, 같은 세션 안에서
사람의 선호가 이만큼 벌어지기는 어렵다. `pause_ratio 0.58`(10초 중 5.8초 침묵)을
함께 보면 **마이크 거리가 달랐거나 한쪽에서 거의 말하지 않은 것**에 가깝다.

판정을 지우지는 않고 `confidence`만 깎는다 — 불확실성의 핸들은 confidence다.
**아직 정하지 못한 것**: 발화량 자체가 부족한 구간(예: `pause_ratio > 0.6`)을
음성 특징에서 제외할 것인가. 심박의 `CONFIDENCE_FLOOR`에 대응하는 음성 쪽 게이트가
없다. 실측이 몇 건 더 쌓여야 임계값을 정할 수 있다.

**특히 불확실한 것**
- **심박 상승의 방향**: 회피/긴장으로 읽었지만 흥분으로도 오른다. 본질적으로 모호해서 단독 판정하지 않고 음성과 교차 검증하도록 했다(반대 방향이면 `contradictory`). 이 처리로 충분한지 확인 필요.
- `f0_std`(억양 변화)는 방향이 모호해 상태축에서 제외했다.
- `hnr`은 음수가 될 수 있어 대칭 비율의 크기가 튈 수 있다. 실측에서 문제가 되는지 확인.

**보류 이유** — 실제 녹음 데이터가 몇 건 쌓여야 의미 있는 조정이 가능하다. 계약을 지키는 한 `[4]` 단계를 통째로 학습 모델로 교체할 수 있게 열어뒀다.

## Q7. STT가 한 번도 성공하지 못했다

**현황 (2026-08-02)**
두 세션 연속으로 발화 구간 3개 전부 `transcript: null`이다. Web Speech API가
한 문장도 받지 못했다.

**고친 것 (그래도 실패)**
- `stop()`이 동기였다 — `recognition.stop()` 직후 결과를 읽었는데, 확정 문장은
  그 뒤에 `onresult`/`onend` 이벤트로 온다. 비동기로 바꿔 `onend`를 기다리게 했다.
- Chrome은 `continuous`를 켜도 침묵이 이어지면 스스로 끝낸다 → 구간이 끝날 때까지 재시작.
- `onerror`가 통째로 삼키고 있었다 → `lastError`로 남기고 콘솔에 경고.

**원인 확인 — 오류 코드는 `network` (발화 구간 3개 전부)**
```
3× useSessionFlow.ts:177  STT 결과 없음 — network
```
Chrome의 Web Speech API는 브라우저 안에서 인식하지 않는다. **오디오를 구글 서버로
보낸다.** `network`는 그 서버에 닿지 못했다는 뜻이므로 우리 코드가 아니라 환경 문제다
(정품 Chrome이 아닌 Chromium 계열이면 API 키가 없어 항상 이 코드가 난다 / VPN / 방화벽).

**여기서 드러난 두 가지**
1. **프라이버시 전제와 충돌한다.** §6에 "프라이버시는 기능이 아니라 전제"라고 써놓고
   사용자 음성을 밝히지도 않은 채 구글로 보내고 있었다. 영상 원본을 서버에 안 보내려고
   들인 공과 앞뒤가 맞지 않는다.
2. **심사위원 환경에서도 똑같이 실패할 수 있다.** 남의 네트워크·브라우저에 의존하는
   시연은 위험하다.

**브라우저에서 음성 특징까지 뽑으면 되지 않나 — 안 된다 (2026-08-02 조사)**

| 지표 | 브라우저 | 근거 |
|---|---|---|
| `f0_mean`, `f0_std` | ✅ | Essentia.js `PitchYin` |
| `loudness_mean` | ✅ | Web Audio |
| `speech_rate`, `pause_ratio` | ✅ | VAD |
| **`jitter_local`** | ❌ | 라이브러리 없음 |
| **`shimmer_local`** | ❌ | 라이브러리 없음 |
| **`hnr`** | ❌ | 라이브러리 없음 |

- Essentia.js에 없다 (Q2에서 조사 완료)
- **openSMILE은 WASM 빌드가 없다**
- Praat도 WASM 포팅이 없다 (parselmouth는 Python 래퍼)
- 직접 구현하려면 주기 단위 피치 마킹이 필요한데, Praat이 정교하게 다루는 부분이라
  급조하면 노이즈만 나온다

이 셋을 얻으려면 **WAV는 어차피 서버로 올라가야 한다.** 그러면 STT만 브라우저로
옮겨도 "음성이 브라우저를 떠나지 않는다"는 얻지 못하고, 얻는 건 "구글이라는 미공개
제3자 제거"뿐이다 — 그건 백엔드 Whisper로도 똑같이 얻는다.

셋을 포기하면 브라우저 완결이 가능하지만, `ENGAGEMENT_SIGN`에서 가중치 합이
**2.1 / 5.7 ≈ 37%**이고 "목소리 떨림·흔들림·맑기"는 비언어 신호 중 가장 특징적인
축이다. 심박이 이미 빠진 상태에서 이것까지 빼면 남는 건 피치와 말속도뿐이라,
제품 정의의 "비언어 신호"라고 부르기 어려워진다.

**해결됨 (2026-08-02) — 백엔드 `faster-whisper` 도입**

계약은 바뀌지 않았다. `transcript` 필드는 그대로이고 채우는 주체만 브라우저 → 서버다.

```
모델      base (int8, CPU)      최초 1회 약 145MB 다운로드
소요      구간당 0.6~0.7초       (모델 로드 후)
전체      /analyze 4초           3구간 합산 — "기록을 정리하고 있어요" 뒤에 묻힌다
```

실제 녹음 인식 결과:
> "오늘 아침에는 일어나서 어제 온 열려 같은 거 있는지 확인을 하고 방송을 좀 보다가
> 다시 프로젝트를 제기를 했어. 어제 하던 거 이어서"

완벽하지 않다(고유명사·조사에서 흔들린다). 그러나 `transcript`는 `[5]`의 **부가**
재료이고 판정은 음향 특징에서 나오므로 이 정도면 충분하다. 품질을 올리려면
`WHISPER_MODEL=small`(약 480MB)로 바꾸면 된다.

**설계 결정 두 가지**
1. **캡처 업로드가 아니라 `[5]` 직전에 돌린다.** 업로드마다 인식하면 세션 단계
   사이에서 사용자가 기다리게 된다. 분석 구간에는 이미 대기 화면이 떠 있다.
2. **브라우저 STT 결과를 덮어쓰지 않는다.** 서버 인식은 폴백이지 대체가 아니다.
   Web Speech가 되는 환경에서는 그쪽이 더 빠르다.

없어도 파이프라인은 돈다 — 설치 실패나 모델 다운로드 실패는 조용히 `None`으로
넘어간다. `STT_ENABLED=false`로 끌 수도 있다.

**남은 것** — Web Speech가 여전히 먼저 시도되고 실패한다(무해하지만 콘솔 경고가
남는다). 프라이버시 관점에서는 **아예 빼는 게 맞다**: 성공하면 사용자 음성이
구글로 가는데, 그 사실을 어디에도 밝히지 않았다. 서버 인식이 되는 지금은
브라우저 STT를 제거하는 편이 프라이버시 서사와 일관된다.

## Q5. 가치관 레이어의 축(axis) 추출

고민들을 가로질러 반복되는 가치 축을 뽑아야 가치관 지도가 그려진다.
- LLM이 선택지에서 축을 추출 ("안정 vs 성장", "관계 vs 자율")
- 축 체계를 미리 고정할 것인가, 자유 생성 후 사후 클러스터링할 것인가
- 몇 세션이 쌓여야 의미 있는 지도가 되는가

**보류 이유** — 세션 데이터가 실제로 쌓여봐야 판단 가능.
